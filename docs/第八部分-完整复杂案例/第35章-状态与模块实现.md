# 第35章-状态与模块实现

## 35.1 架构落地时，先不要急着写节点

第 34 章已经把智能研究助理的系统架构拆清楚了。

我们知道它包含这些核心模块：

```text
memory_loader
router
planner
human_approval
dispatch_research
researcher
tool_executor
state_aggregator
reviewer
writer
memory_writer
```

现在很容易产生一个冲动：

```text
马上开始写这些节点函数。
```

但复杂 Agent 最容易出问题的地方，往往不是某个节点函数写错了，而是共享状态一开始就没有设计好。

如果 State 设计混乱，后面会出现这些问题：

```text
Router 写的 task_type，Planner 不知道怎么用。
Planner 生成的 subtasks，Researcher 不知道哪个是当前任务。
Tool Executor 返回的结果，Researcher 和 Aggregator 都读不稳定。
Reviewer 提出的反馈，Planner 不知道是否该修订计划。
Writer 直接读取原始工具结果，绕过了 Aggregator。
Memory 和 Checkpoint 被混成一团。
```

这些问题表面上像“节点逻辑不清楚”。

但根源通常是：

> 复杂 Agent 的共享状态没有主线，模块之间没有清楚的数据契约。

所以本章采用“状态主线法”。

我们先不急着实现完整图，而是沿着一条状态演化路线来设计：

```text
topic
-> task_type
-> research_plan
-> approval_status
-> active_subtask
-> tool_requests
-> tool_results
-> findings
-> synthesis
-> review_feedback
-> final_report
```

这条线就是智能研究助理的脊柱。

每个模块都只负责推动其中一段状态变化。

## 35.2 本章要解决的问题

本章的核心问题是：

> 复杂 Agent 的共享状态如何设计，模块边界如何划分？

具体来说，我们要回答五个问题。

第一，完整 `ResearchState` 应该包含哪些字段？

第二，哪些字段属于输入，哪些属于运行中间状态，哪些属于输出？

第三，哪些字段会被多个模块追加写入，需要 reducer？

第四，每个模块应该读取哪些字段、写入哪些字段？

第五，如何用简单可运行的节点骨架，证明这些边界是可实现的？

本章不会追求一次写出生产级完整代码。

第八部分的复杂案例要分几章展开。

本章先做两件最关键的事：

```text
把 State 契约立起来。
把模块读写边界立起来。
```

只要这两件事清楚，第 36 章接入 Ollama 与 DeepSeek、第 37 章加入 checkpoint 与人工审批、第 38 章完整运行，都会更稳。

## 35.3 错误写法：一个万能 ResearchState

先看一个不好的状态设计。

```python
from typing import TypedDict


class ResearchState(TypedDict, total=False):
    topic: str
    data: dict
    result: str
    status: str
    current: dict
    messages: list
    output: str
    error: str
```

这段 State 看起来很短。

但它的问题很大。

第一，字段太泛。

`data`、`result`、`current`、`output` 这些名字都看不出生命周期。

读者不知道 `result` 是工具结果、研究发现、审查结果，还是最终报告。

第二，模块边界不清。

Router 可以写 `data`。

Planner 也可以写 `data`。

Tool Executor 也可以写 `data`。

最后没人知道 `data` 里到底是谁的产物。

第三，控制流很难写。

条件边需要读取明确字段。

例如：

```text
approval_status
quality_status
next_action
```

如果只有一个 `status`，很快会混乱：

```text
status 是计划审批状态？
还是工具执行状态？
还是审查质量状态？
还是整个图的完成状态？
```

第四，测试困难。

测试 Planner 时，你需要知道它应该写哪个字段。

如果只是写 `data["plan"]`，测试和实现都容易变成约定俗成的隐式协议。

所以复杂 Agent 的 State 不能靠几个万能字段撑起来。

它需要把业务状态的演化路径显式写出来。

## 35.4 状态主线：从主题到报告

智能研究助理的状态主线可以分成七段。

```mermaid
flowchart LR
  A["输入: topic"] --> B["路由: task_type"]
  B --> C["计划: research_plan / subtasks"]
  C --> D["执行: tool_requests / tool_results"]
  D --> E["发现: findings"]
  E --> F["聚合: synthesis / evidence_map"]
  F --> G["审查: review_feedback / quality_status"]
  G --> H["输出: final_report"]
```

这张图不是执行图。

它是状态演化图。

它告诉我们：

```text
每个阶段应该产生什么状态。
后一个阶段依赖前一个阶段的哪些结果。
哪些字段是主线字段，哪些只是辅助字段。
```

这和第 34 章的模块架构对应起来就是：

| 状态阶段 | 主要模块 | 核心字段 |
| --- | --- | --- |
| 输入 | 应用入口 / Memory | `topic`, `user_id`, `user_preferences` |
| 路由 | Router | `task_type`, `route_reason` |
| 计划 | Planner / Human Approval | `research_plan`, `subtasks`, `approval_status` |
| 执行 | Dispatcher / Researcher / Tool Executor | `active_subtask`, `research_status`, `tool_requests`, `tool_results` |
| 发现 | Researcher | `findings`, `completed_subtasks` |
| 聚合 | State Aggregator | `synthesis`, `evidence_map` |
| 审查 | Reviewer | `review_feedback`, `quality_status`, `next_action` |
| 输出 | Writer / Memory Writer | `final_report`, `report_metadata`, `memory_updates` |

如果一个字段无法放进这条主线，就要谨慎。

它可能只是节点内部临时变量。

它也可能应该进入日志、streaming event 或外部数据库，而不是进入 State。

## 35.5 先定义基础枚举

为了避免字符串到处乱飞，先定义几个 `Literal`。

```python
from typing import Literal


TaskType = Literal[
    "concept_research",
    "architecture_research",
    "comparison_research",
    "implementation_plan",
]

ApprovalStatus = Literal[
    "pending",
    "approved",
    "needs_revision",
    "rejected",
]

ToolStatus = Literal[
    "pending",
    "success",
    "failed",
]

QualityStatus = Literal[
    "approved",
    "needs_revision",
]

ResearchStatus = Literal[
    "has_subtask",
    "all_done",
]

NextAction = Literal[
    "write_report",
    "revise_plan",
    "more_research",
]
```

为什么要先写这些类型？

因为复杂 Agent 里很多控制流都依赖状态值。

例如 Human Approval 后面的条件边会读：

```text
approval_status
```

Reviewer 后面的条件边会读：

```text
next_action
```

如果这些值只是任意字符串，很容易出现：

```text
approved
approve
pass
passed
```

条件边映射时就会出错。

用 `Literal` 至少能让字段取值更清楚，也方便测试。

## 35.6 定义核心结构：计划、子任务、工具请求、工具结果

接下来定义几个结构化对象。

不要把所有嵌套数据都写成 `dict`。

至少要给关键结构起名字。

### 研究子任务

```python
from typing import TypedDict


class ResearchSubtask(TypedDict):
    id: str
    question: str
    expected_output: str
    priority: int
```

一个子任务至少要说明：

```text
任务 id 是什么。
要回答什么问题。
期望产出是什么。
优先级是什么。
```

例如：

```python
{
    "id": "modularity",
    "question": "LangGraph 如何帮助复杂 Agent 做模块化设计？",
    "expected_output": "模块化设计原则和边界说明",
    "priority": 1,
}
```

### 研究计划

```python
class ResearchPlan(TypedDict):
    plan_id: str
    goal: str
    version: int
    subtasks: list[ResearchSubtask]
```

计划不是一段自然语言。

它应该包含目标、版本和子任务列表。

版本很重要。

因为后面 Reviewer 或用户可能要求修改计划。

如果没有版本，调试时很难知道当前结果是基于哪一版计划产生的。

### 工具请求

```python
class ToolRequest(TypedDict):
    id: str
    subtask_id: str
    tool_name: str
    query: str
    purpose: str
```

工具请求是 Researcher 写给 Tool Executor 的任务单。

它要说明：

```text
哪个子任务需要这个工具。
调用哪个工具。
输入是什么。
为什么要调用。
```

Tool Executor 不应该猜研究意图。

它只执行结构化请求。

### 工具结果

```python
class ToolResult(TypedDict, total=False):
    request_id: str
    subtask_id: str
    tool_name: str
    status: ToolStatus
    content: str
    source_id: str
    error: str
```

工具结果必须带上 `request_id` 和 `subtask_id`。

否则后面很难把结果追溯到哪个子任务。

`status` 也很重要。

工具失败不是异常地消失，而应该进入状态，后续节点才能决定重试、跳过或报告风险。

## 35.7 定义发现、聚合和审查结构

研究助理不是收集资料就结束。

资料要变成发现，发现要变成聚合结论，结论还要被审查。

所以继续定义三类结构。

### 研究发现

```python
class Finding(TypedDict):
    subtask_id: str
    summary: str
    evidence_ids: list[str]
```

`Finding` 是 Researcher 的主要产物。

它不是原始资料。

它是针对某个子任务得到的解释性结论。

例如：

```python
{
    "subtask_id": "checkpoint",
    "summary": "Checkpoint 让 LangGraph 可以按 thread_id 恢复长任务执行现场。",
    "evidence_ids": ["source-checkpoint-1"],
}
```

### 聚合结论

```python
class Synthesis(TypedDict):
    thesis: str
    key_points: list[str]
    gaps: list[str]
```

`Synthesis` 是 State Aggregator 的产物。

它把多个子任务发现合成一个中间结论。

这里故意保留 `gaps`。

因为聚合时可能发现资料不足。

例如：

```text
模块化、checkpoint、人机协作都有发现，但对“未来扩展”的资料不足。
```

这个缺口应该进入 State，让 Reviewer 能看见。

### 审查反馈

```python
class ReviewFeedback(TypedDict):
    passed: bool
    issues: list[str]
    suggestions: list[str]
    next_action: NextAction
```

Reviewer 不应该只返回一句：

```text
还可以更好。
```

它应该返回结构化反馈。

否则 Planner、Researcher 和 Writer 都不知道下一步该做什么。

`next_action` 是控制流字段。

它会决定 Reviewer 之后走向哪里：

```text
write_report -> Writer
revise_plan -> Planner
more_research -> Dispatcher / Researcher
```

## 35.8 定义错误、报告和记忆结构

复杂 Agent 必须面对失败，也要明确输出和记忆边界。

### 错误记录

```python
class ErrorRecord(TypedDict):
    node: str
    error_type: str
    message: str
```

不要只用一个 `error: str`。

如果错误会影响控制流，至少要知道：

```text
哪个节点出错。
错误类型是什么。
错误信息是什么。
```

后面第 37 章做恢复和人工审批时，这些信息会很有用。

### 报告元数据

```python
class ReportMetadata(TypedDict):
    plan_version: int
    source_count: int
    finding_count: int
```

最终报告不只是一段文本。

至少应该知道：

```text
它基于哪一版计划。
用了多少资料。
汇总了多少发现。
```

这会让结果更可追踪。

### 用户偏好

```python
class UserPreferences(TypedDict, total=False):
    preferred_style: str
    focus: list[str]
```

本案例先用简单偏好结构。

例如：

```python
{
    "preferred_style": "先讲问题，再讲架构决策，最后讲扩展",
    "focus": ["模块化", "可扩展性", "生产化"],
}
```

以后可以把它换成外部 store、向量记忆或用户画像服务。

但在 State 里，节点只需要看到一个稳定的 `user_preferences` 字段。

## 35.9 组合完整 ResearchState

现在可以组合完整 State。

```python
from operator import add
from typing import Annotated, TypedDict


class ResearchInput(TypedDict, total=False):
    topic: str
    user_id: str
    thread_id: str


class ResearchOutput(TypedDict, total=False):
    final_report: str
    report_metadata: ReportMetadata


class ResearchState(ResearchInput, ResearchOutput, total=False):
    # 记忆与路由
    user_preferences: UserPreferences
    task_type: TaskType
    route_reason: str

    # 计划与审批
    research_plan: ResearchPlan
    plan_version: int
    subtasks: list[ResearchSubtask]
    approval_status: ApprovalStatus
    approval_feedback: str

    # 研究执行
    active_subtask: ResearchSubtask
    research_status: ResearchStatus
    completed_subtasks: Annotated[list[str], add]
    tool_requests: Annotated[list[ToolRequest], add]
    tool_results: Annotated[list[ToolResult], add]

    # 发现与聚合
    findings: Annotated[list[Finding], add]
    synthesis: Synthesis
    evidence_map: dict[str, list[str]]

    # 审查与控制流
    review_feedback: ReviewFeedback
    quality_status: QualityStatus
    next_action: NextAction

    # 运行记录
    memory_updates: dict
    execution_log: Annotated[list[str], add]
    errors: Annotated[list[ErrorRecord], add]
```

这段 State 比前面章节的示例大很多。

但它不是乱的。

它按生命周期分成了几块：

```text
输入。
记忆与路由。
计划与审批。
研究执行。
发现与聚合。
审查与控制流。
输出。
运行记录。
```

复杂 Agent 的 State 不怕字段多。

怕的是字段没有边界。

## 35.10 哪些字段需要 reducer

上面的 State 里，有些字段使用了 `Annotated[..., add]`。

这些字段的共同特点是：

```text
多个节点可能追加写入。
历史记录有价值。
后写不应该覆盖前写。
```

例如：

```python
completed_subtasks: Annotated[list[str], add]
tool_requests: Annotated[list[ToolRequest], add]
tool_results: Annotated[list[ToolResult], add]
findings: Annotated[list[Finding], add]
execution_log: Annotated[list[str], add]
errors: Annotated[list[ErrorRecord], add]
```

为什么需要 reducer？

假设 Researcher 连续处理两个子任务。

第一个子任务返回：

```python
{"findings": [{"subtask_id": "modularity", "summary": "...", "evidence_ids": ["s1"]}]}
```

第二个子任务返回：

```python
{"findings": [{"subtask_id": "checkpoint", "summary": "...", "evidence_ids": ["s2"]}]}
```

如果没有追加语义，第二次写入可能覆盖第一次。

最终 State 只剩最后一个发现。

这对研究助理是灾难。

所以凡是“历史累积型字段”，都应该明确合并语义。

但不是所有字段都要追加。

这些字段更适合覆盖：

| 字段 | 为什么覆盖 |
| --- | --- |
| `task_type` | 当前任务只有一个主要类型 |
| `research_plan` | 当前计划以最新版本为准 |
| `active_subtask` | 当前只处理一个子任务 |
| `synthesis` | 聚合结论以最新聚合为准 |
| `review_feedback` | 当前审查意见以最新一轮为准 |
| `final_report` | 最终报告以最后版本为准 |

Reducer 不是语法细节。

它是状态语义的一部分。

## 35.11 模块边界：每个节点只推动一段状态

有了 State，接下来定义模块边界。

一个简单原则是：

> 每个模块只推动状态主线中的一段，不跨段抢职责。

可以先看总表。

| 模块 | 读取字段 | 写入字段 |
| --- | --- | --- |
| `memory_loader` | `user_id` | `user_preferences`, `execution_log` |
| `router` | `topic`, `user_preferences` | `task_type`, `route_reason`, `execution_log` |
| `planner` | `topic`, `task_type`, `user_preferences`, `review_feedback`, `approval_feedback` | `research_plan`, `plan_version`, `subtasks`, `approval_status`, `execution_log` |
| `human_approval` | `research_plan` | `approval_status`, `approval_feedback`, `execution_log` |
| `dispatch_research` | `subtasks`, `completed_subtasks` | `active_subtask`, `research_status`, `execution_log` |
| `researcher` | `active_subtask`, `tool_results` | `tool_requests`, `findings`, `completed_subtasks`, `execution_log` |
| `tool_executor` | `tool_requests` | `tool_results`, `errors`, `execution_log` |
| `state_aggregator` | `subtasks`, `tool_results`, `findings` | `synthesis`, `evidence_map`, `execution_log` |
| `reviewer` | `topic`, `research_plan`, `synthesis`, `evidence_map`, `user_preferences` | `review_feedback`, `quality_status`, `next_action`, `execution_log` |
| `writer` | `topic`, `research_plan`, `synthesis`, `evidence_map`, `review_feedback`, `user_preferences` | `final_report`, `report_metadata`, `execution_log` |
| `memory_writer` | `approval_feedback`, `final_report`, `review_feedback` | `memory_updates`, `execution_log` |

这张表比代码还重要。

因为它告诉我们：

```text
模块之间通过 State 通信。
每个模块只写自己负责的字段。
如果一个模块开始写不该写的字段，边界就坏了。
```

例如 Writer 不应该写 `findings`。

Reviewer 不应该写 `final_report`。

Tool Executor 不应该写 `synthesis`。

这些约束会让复杂 Agent 更容易测试和维护。

## 35.12 实现辅助函数：日志和子任务选择

为了让后面的节点代码简洁，先定义两个辅助函数。

第一个是追加日志。

```python
def log(message: str) -> list[str]:
    return [message]
```

因为 `execution_log` 使用追加 reducer，所以节点只需要返回当前这条日志：

```python
return {"execution_log": log("router 判断任务类型")}
```

第二个是选择下一个未完成子任务。

```python
def pick_next_subtask(
    subtasks: list[ResearchSubtask],
    completed: list[str],
) -> ResearchSubtask | None:
    completed_set = set(completed)

    for subtask in sorted(subtasks, key=lambda item: item["priority"]):
        if subtask["id"] not in completed_set:
            return subtask

    return None
```

这个函数应该保持纯粹。

它不读模型。

不调用工具。

不修改状态。

它只是根据子任务列表和已完成列表，选择下一个任务。

这样就很容易单独测试。

## 35.13 memory_loader：读取长期偏好

`memory_loader` 是入口节点。

本章先用固定偏好模拟长期记忆。

```python
def memory_loader(state: ResearchState) -> dict:
    preferences: UserPreferences = {
        "preferred_style": "先讲问题，再讲架构决策，最后讲扩展",
        "focus": ["模块化", "可扩展性", "生产化"],
    }

    return {
        "user_preferences": preferences,
        "execution_log": log("memory_loader 读取用户偏好"),
    }
```

它只写 `user_preferences`。

它不判断任务类型。

不生成计划。

不写报告。

这就是边界。

后面第 37 章可以把这里替换成真正的 store。

但只要输出仍然是 `user_preferences`，其他模块不用改。

## 35.14 router：只判断任务类型

Router 读取 `topic` 和 `user_preferences`，写入 `task_type` 与 `route_reason`。

```python
def router(state: ResearchState) -> dict:
    topic = state["topic"]

    if "比较" in topic or "对比" in topic:
        task_type: TaskType = "comparison_research"
        reason = "主题要求比较多个对象"
    elif "架构" in topic or "可扩展" in topic or "模块化" in topic:
        task_type = "architecture_research"
        reason = "主题关注架构设计、模块化或扩展能力"
    elif "方案" in topic or "计划" in topic:
        task_type = "implementation_plan"
        reason = "主题要求输出实施方案或行动计划"
    else:
        task_type = "concept_research"
        reason = "主题更接近概念解释或普通研究"

    return {
        "task_type": task_type,
        "route_reason": reason,
        "execution_log": log(f"router 判断任务类型：{task_type}"),
    }
```

这里先用规则模拟。

第 36 章可以替换成 Ollama 或 DeepSeek。

但 Router 的状态契约不变：

```text
输入：topic, user_preferences
输出：task_type, route_reason
```

这就是可替换性的来源。

## 35.15 planner：生成结构化计划

Planner 读取主题、任务类型和偏好，生成研究计划。

```python
def planner(state: ResearchState) -> dict:
    version = state.get("plan_version", 0) + 1
    topic = state["topic"]

    subtasks: list[ResearchSubtask] = [
        {
            "id": "complexity",
            "question": "复杂 Agent 应用的复杂度来自哪里？",
            "expected_output": "复杂度来源和解释",
            "priority": 1,
        },
        {
            "id": "modularity",
            "question": "如何用 LangGraph 设计清晰模块边界？",
            "expected_output": "模块化设计原则",
            "priority": 2,
        },
        {
            "id": "persistence",
            "question": "Checkpoint、Thread、Interrupt 如何支持长任务？",
            "expected_output": "持久化与恢复机制说明",
            "priority": 3,
        },
        {
            "id": "evolution",
            "question": "这个架构未来如何扩展到生产系统？",
            "expected_output": "生产演进建议",
            "priority": 4,
        },
    ]

    plan: ResearchPlan = {
        "plan_id": f"plan-v{version}",
        "goal": f"围绕「{topic}」形成结构化研究报告",
        "version": version,
        "subtasks": subtasks,
    }

    return {
        "research_plan": plan,
        "plan_version": version,
        "subtasks": subtasks,
        "approval_status": "pending",
        "execution_log": log(f"planner 生成第 {version} 版研究计划"),
    }
```

这里有几个设计点。

第一，计划是结构化对象，不是一段自然语言。

第二，计划里包含版本号。

第三，Planner 写入 `approval_status: pending`。

这表示计划生成后，还没有被用户批准。

注意 Planner 不写 `active_subtask`。

选择当前子任务是 `dispatch_research` 的职责。

## 35.16 human_approval：把人工决策写进 State

真实项目里，`human_approval` 会用 `interrupt` 暂停。

本章先用一个简化版本模拟批准。

```python
def human_approval(state: ResearchState) -> dict:
    return {
        "approval_status": "approved",
        "approval_feedback": "计划方向符合需求，可以开始研究。",
        "execution_log": log("human_approval 用户批准研究计划"),
    }
```

这个节点只做一件事：

```text
把用户决策写回 State。
```

它不修改计划。

如果用户要求修改计划，它应该写：

```python
{
    "approval_status": "needs_revision",
    "approval_feedback": "弱化 RAG，重点讲模块化和未来扩展。",
}
```

然后条件边把流程送回 Planner。

人工节点不亲自改计划。

这能保持职责清楚。

## 35.17 dispatch_research：选择当前子任务

`dispatch_research` 负责从 `subtasks` 中找下一个未完成任务。

```python
def dispatch_research(state: ResearchState) -> dict:
    next_subtask = pick_next_subtask(
        state.get("subtasks", []),
        state.get("completed_subtasks", []),
    )

    if next_subtask is None:
        return {
            "research_status": "all_done",
            "execution_log": log("dispatch_research 所有子任务已完成"),
        }

    return {
        "active_subtask": next_subtask,
        "research_status": "has_subtask",
        "execution_log": log(f"dispatch_research 分发子任务：{next_subtask['id']}"),
    }
```

这个节点有点像一个轻量 Supervisor。

但它的职责很窄：

```text
只选择下一个子任务。
```

它不分析资料。

不生成工具请求。

不写发现。

这能避免 Planner、Dispatcher、Researcher 的职责混在一起。

## 35.18 researcher：把子任务变成工具请求和发现

Researcher 负责两件事。

第一，如果当前子任务还没有工具结果，就生成工具请求。

第二，如果已经有工具结果，就提取研究发现。

为了让本章简单，我们先写成确定性逻辑。

```python
def researcher(state: ResearchState) -> dict:
    subtask = state["active_subtask"]
    subtask_id = subtask["id"]

    related_results = [
        result
        for result in state.get("tool_results", [])
        if result["subtask_id"] == subtask_id and result["status"] == "success"
    ]

    if not related_results:
        request: ToolRequest = {
            "id": f"tool-{subtask_id}",
            "subtask_id": subtask_id,
            "tool_name": "search_docs",
            "query": subtask["question"],
            "purpose": subtask["expected_output"],
        }

        return {
            "tool_requests": [request],
            "execution_log": log(f"researcher 为子任务 {subtask_id} 生成工具请求"),
        }

    finding: Finding = {
        "subtask_id": subtask_id,
        "summary": f"围绕「{subtask['question']}」得到研究发现：{related_results[-1]['content']}",
        "evidence_ids": [related_results[-1].get("source_id", f"source-{subtask_id}")],
    }

    return {
        "findings": [finding],
        "completed_subtasks": [subtask_id],
        "execution_log": log(f"researcher 完成子任务发现：{subtask_id}"),
    }
```

注意它没有直接调用搜索工具。

它只生成 `tool_requests`。

工具执行交给 `tool_executor`。

这样 Researcher 可以单独测试：

```text
没有 tool_results 时，是否生成工具请求？
有 tool_results 时，是否生成 finding？
```

## 35.19 tool_executor：统一执行工具请求

本章先用模拟工具结果。

真实工具接入放到后续章节继续升级。

```python
def tool_executor(state: ResearchState) -> dict:
    executed_ids = {
        result["request_id"]
        for result in state.get("tool_results", [])
    }

    pending_requests = [
        request
        for request in state.get("tool_requests", [])
        if request["id"] not in executed_ids
    ]

    results: list[ToolResult] = []

    for request in pending_requests:
        results.append(
            {
                "request_id": request["id"],
                "subtask_id": request["subtask_id"],
                "tool_name": request["tool_name"],
                "status": "success",
                "content": f"模拟资料：{request['query']} 的关键资料摘要。",
                "source_id": f"source-{request['subtask_id']}",
            }
        )

    return {
        "tool_results": results,
        "execution_log": log(f"tool_executor 执行 {len(results)} 个工具请求"),
    }
```

这里的关键不是模拟结果，而是协议。

Tool Executor 读取：

```text
tool_requests
```

写入：

```text
tool_results
```

它不写 `findings`。

因为它不负责解释研究意义。

它也不写 `synthesis`。

因为它不负责聚合结论。

## 35.20 state_aggregator：把发现聚合成中间结论

当所有子任务完成后，State 里会有多个 `findings`。

Aggregator 要把这些发现整理成 `synthesis` 和 `evidence_map`。

```python
def state_aggregator(state: ResearchState) -> dict:
    findings = state.get("findings", [])
    key_points = [finding["summary"] for finding in findings]

    evidence_map = {
        finding["subtask_id"]: finding["evidence_ids"]
        for finding in findings
    }

    synthesis: Synthesis = {
        "thesis": "复杂 Agent 架构的核心是把状态、模块、工具、审查和恢复能力放进清晰边界。",
        "key_points": key_points,
        "gaps": [] if len(findings) >= len(state.get("subtasks", [])) else ["仍有子任务未完成"],
    }

    return {
        "synthesis": synthesis,
        "evidence_map": evidence_map,
        "execution_log": log("state_aggregator 聚合研究发现"),
    }
```

Aggregator 不写最终报告。

它输出的是可审查的中间结论。

这一步很重要。

如果跳过 Aggregator，Writer 就会直接面对一堆碎片化 findings 和 tool_results。

报告质量会过度依赖模型临场发挥。

## 35.21 reviewer：检查中间结论是否足够

Reviewer 读取 `synthesis`，写入结构化审查结果。

```python
def reviewer(state: ResearchState) -> dict:
    synthesis = state["synthesis"]
    issues: list[str] = []
    suggestions: list[str] = []

    if synthesis["gaps"]:
        issues.extend(synthesis["gaps"])
        suggestions.append("补充未完成子任务的研究发现")

    if "模块" not in synthesis["thesis"] and "边界" not in synthesis["thesis"]:
        issues.append("中间结论没有突出模块边界")
        suggestions.append("补充模块化和边界设计相关结论")

    passed = not issues
    next_action: NextAction = "write_report" if passed else "more_research"

    feedback: ReviewFeedback = {
        "passed": passed,
        "issues": issues,
        "suggestions": suggestions,
        "next_action": next_action,
    }

    return {
        "review_feedback": feedback,
        "quality_status": "approved" if passed else "needs_revision",
        "next_action": next_action,
        "execution_log": log("reviewer 完成研究质量审查"),
    }
```

Reviewer 不修改 `synthesis`。

不写 `final_report`。

它只判断：

```text
当前研究是否足够进入写作。
```

这和第 34 章的边界一致。

## 35.22 writer：基于审查通过的结论写报告

Writer 读取 `synthesis`、`evidence_map`、`research_plan` 和用户偏好。

然后写入 `final_report`。

```python
def writer(state: ResearchState) -> dict:
    synthesis = state["synthesis"]
    plan = state["research_plan"]

    lines = [
        f"# {state['topic']}",
        "",
        "## 核心结论",
        synthesis["thesis"],
        "",
        "## 关键发现",
    ]

    for point in synthesis["key_points"]:
        lines.append(f"- {point}")

    lines.extend(
        [
            "",
            "## 架构建议",
            "把复杂 Agent 拆成职责清晰的模块，并通过 State 传递结构化中间结果。",
            "让 Reviewer 在 Writer 之前执行，避免资料不足时直接生成顺滑但不可靠的报告。",
            "把 Tool Executor 独立出来，统一处理工具风险、错误和重试。",
        ]
    )

    metadata: ReportMetadata = {
        "plan_version": plan["version"],
        "source_count": len(state.get("tool_results", [])),
        "finding_count": len(state.get("findings", [])),
    }

    return {
        "final_report": "\n".join(lines),
        "report_metadata": metadata,
        "execution_log": log("writer 生成最终研究报告"),
    }
```

Writer 的边界要守住。

它不再生成新工具请求。

不补充 findings。

不绕过 Reviewer。

它只把已经审查过的结论组织成报告。

本案例先用一个简单节点模拟记忆更新。

```python
def memory_writer(state: ResearchState) -> dict:

```

注意它写的是 `memory_updates`。


## 35.24 条件边依赖哪些状态

有了这些模块以后，图的条件边就可以围绕少数字段设计。

### 计划审批之后

```python
def decide_after_approval(state: ResearchState) -> str:
    return state["approval_status"]
```

映射关系：

```text
approved -> dispatch_research
needs_revision -> planner
rejected -> END
```

### Researcher 之后

```python
def decide_after_researcher(state: ResearchState) -> str:
    subtask_id = state["active_subtask"]["id"]

    has_result = any(
        result["subtask_id"] == subtask_id
        for result in state.get("tool_results", [])
    )

    has_finding = any(
        finding["subtask_id"] == subtask_id
        for finding in state.get("findings", [])
    )

    if not has_result:
        return "tool_executor"

    if not has_finding:
        return "researcher"

    return "dispatch_research"
```

这个路由函数体现了状态主线：

```text
没有 tool_result，先去工具。
有 tool_result 但没有 finding，回到 researcher 提取发现。
有 finding，回到 dispatcher 处理下一个子任务。
```

### Dispatcher 之后

```python
def decide_after_dispatch(state: ResearchState) -> str:
    if state["research_status"] == "all_done":
        return "state_aggregator"

    return "researcher"
```

这里不要用 `active_subtask` 是否存在来判断。

因为子任务完成后，旧的 `active_subtask` 可能仍然留在 State 里。

更稳妥的方式是让 `dispatch_research` 显式写入 `research_status`。

这样条件边只依赖明确控制字段。

### Reviewer 之后

```python
def decide_after_review(state: ResearchState) -> str:
    return state["next_action"]
```

映射关系：

```text
write_report -> writer
revise_plan -> planner
more_research -> dispatch_research
```

可以看到，条件边不需要理解所有业务。

它们只读取少数控制字段：

```text
approval_status
active_subtask
tool_results
findings
next_action
```

这就是状态设计清楚之后带来的好处。

## 35.25 图组装预览

完整图会在后续章节继续完善。

本章先给出结构预览：

```python
from langgraph.graph import END, START, StateGraph


def build_research_graph():
    builder = StateGraph(ResearchState)

    builder.add_node("memory_loader", memory_loader)
    builder.add_node("router", router)
    builder.add_node("planner", planner)
    builder.add_node("human_approval", human_approval)
    builder.add_node("dispatch_research", dispatch_research)
    builder.add_node("researcher", researcher)
    builder.add_node("tool_executor", tool_executor)
    builder.add_node("state_aggregator", state_aggregator)
    builder.add_node("reviewer", reviewer)
    builder.add_node("writer", writer)
    builder.add_node("memory_writer", memory_writer)

    builder.add_edge(START, "memory_loader")
    builder.add_edge("memory_loader", "router")
    builder.add_edge("router", "planner")
    builder.add_edge("planner", "human_approval")
    builder.add_conditional_edges(
        "human_approval",
        decide_after_approval,
        {
            "approved": "dispatch_research",
            "needs_revision": "planner",
            "rejected": END,
        },
    )
    builder.add_conditional_edges(
        "dispatch_research",
        decide_after_dispatch,
        {
            "researcher": "researcher",
            "state_aggregator": "state_aggregator",
        },
    )
    builder.add_conditional_edges(
        "researcher",
        decide_after_researcher,
        {
            "tool_executor": "tool_executor",
            "researcher": "researcher",
            "dispatch_research": "dispatch_research",
        },
    )
    builder.add_edge("tool_executor", "researcher")
    builder.add_edge("state_aggregator", "reviewer")
    builder.add_conditional_edges(
        "reviewer",
        decide_after_review,
        {
            "write_report": "writer",
            "revise_plan": "planner",
            "more_research": "dispatch_research",
        },
    )
    builder.add_edge("writer", "memory_writer")
    builder.add_edge("memory_writer", END)

    return builder.compile()
```

这段代码的重点不是让你马上复制运行。

它的重点是：

```text
每条边都能从状态字段解释。
每个节点都只写自己负责的状态。
图结构和 State 主线互相对应。
```

## 35.27 常见错误与排查

### 错误一：Writer 直接读取 tool_results

现象：

```text
Writer 跳过 synthesis，直接把工具结果写成报告。
```

问题：

```text
报告结构过度依赖模型临场整理，来源与结论关系不清。
```

建议：

```text
让 Aggregator 先生成 synthesis 和 evidence_map，Writer 只基于聚合结论写作。
```

### 错误二：Reviewer 直接修改 final_report

现象：

```text
Reviewer 既审查又顺手重写报告。
```

问题：

```text
审查和表达混在一起，质量闸门失效。
```

建议：

```text
Reviewer 只写 review_feedback、quality_status、next_action。
```

### 错误三：Tool Executor 写入 findings

现象：

```text
工具执行节点直接生成研究发现。
```

问题：

```text
工具执行和研究解释混在一起，工具模块难以复用。
```

建议：

```text
Tool Executor 只写 tool_results，由 Researcher 解释工具结果。
```

### 错误四：completed_subtasks 被覆盖

现象：

```text
多个子任务完成后，State 里只剩最后一个 completed_subtasks。
```

问题：

```text
字段没有追加 reducer。
```

建议：

```text
使用 Annotated[list[str], add]，每次只返回当前完成的 subtask_id。
```

### 错误五：审批状态和质量状态混用

现象：

```text
approval_status 既表示用户是否批准计划，也表示 Reviewer 是否通过。
```

问题：

```text
Human Approval 和 Reviewer 的控制流混在一起。
```

建议：

```text
计划审批用 approval_status，研究质量用 quality_status，下一步控制用 next_action。
```

## 35.28 本章小结

本章把第 34 章的架构设计推进到了状态和模块实现。

我们没有先写一个大节点，而是沿着状态主线设计：

```text
topic
-> task_type
-> research_plan
-> approval_status
-> active_subtask
-> tool_requests
-> tool_results
-> findings
-> synthesis
-> review_feedback
-> final_report
```

然后我们定义了关键结构：

```text
ResearchSubtask
ResearchPlan
ToolRequest
ToolResult
Finding
Synthesis
ReviewFeedback
ErrorRecord
ReportMetadata
UserPreferences
ResearchState
```

接着我们把模块边界落到读写关系上：

```text
Router 只写 task_type 和 route_reason。
Planner 只写 research_plan、subtasks 和计划状态。
Researcher 生成 tool_requests 或 findings。
Tool Executor 只写 tool_results。
Aggregator 只写 synthesis 和 evidence_map。
Reviewer 只写 review_feedback、quality_status、next_action。
Writer 只写 final_report 和 report_metadata。
```

本章最重要的结论是：

> 复杂 Agent 的模块边界，最终要落到 State 的读写边界上。

如果 State 主线清楚，节点就不会乱写。

如果节点边界清楚，图结构就容易调试。

如果图结构和状态主线对应起来，复杂 Agent 才能真正可维护、可扩展、可恢复。
